# 跨批次安全汇总发布工作台（init / preview / release / receipt）

数据团队要向不同合作方持续提供**同一份**固定私有频数向量 `x` 的分类子集汇总。
单个"类别子集原始计数和"本身不暴露任何受保护类别的频数，但两个各自安全的汇总
可以通过精确相减组合出受保护类别的频数（例如公开 `{a,b}` 与 `{b}` 后，`a` 的频数
即被确定）。本工作台把每一次已公开的等式永久记入公开知识账本，每次发布都针对
**提交时刻的完整历史**重新做精确安全判定与全局最优选择。仅用 Python 标准库与
SQLite；本题不计算新的 PSI、不做实体配对、修订链或时间窗口。

## 1. 数据契约

### 1.1 私有向量（init）

严格 JSON，**恰好**三个字段：

```json
{"categories": ["a", "b", "c"],
 "counts": [{"category": "a", "count": 100}, {"category": "b", "count": 20},
            {"category": "c", "count": 7}],
 "protected": ["a"]}
```

* `categories`：2..32 个唯一 `common.ident` 字符串；
* `counts`：每个声明类别**恰好一次**的 `{"category","count"}`，`count` 沿用
  现有 0..10⁹ 严格整数语义（`type(x) is int`，布尔拒绝）；
* `protected`：非空、唯一的声明类别子集。

每库只对应这一份固定私有向量 `x`：init 时把规范化（各数组排序后的）规范文本写入
`meta.config` 并固定，初始化后不得改值或改保护域。**三个数组的顺序不构成身份**，
标识符精确匹配：相同规范字段值重开幂等（`status=unchanged`），任何差异拒绝。
输入沿用严格 JSON：重复键/未知字段拒绝、`NaN/Infinity` 拒绝、8 MB 上限。

### 1.2 发布请求（preview / release）

严格 JSON，**恰好** `{"request_id","queries"}`：

```json
{"request_id": "partner-batch-1",
 "queries": [{"id": "q-ab", "members": ["a", "b"], "utility": 5}]}
```

* `queries`：非空、最多 22 条，每条恰好 `{"id","members","utility"}`；
* `request_id` 与 `id` 沿用 `common.ident`；`id` 在本请求内唯一；
* `members`：非空、唯一的声明类别子集；不同 `id` 允许相同 `members`；
* `utility`：1..10⁶ 严格整数；
* **成员和 query 数组顺序不影响请求身份**；utility 和任何集合内容改变都构成
  不同请求。规范身份 = 将 queries 按 id 排序、members 排序后的规范 JSON 及其
  SHA-256。

一个 query 的公开数据是其成员类别的**原始计数之和**：不平滑、不四舍五入，
可以超过单类 10⁹（Python 整数精确求和）。所有合作方共享同一公开知识：
账本只有一份，不能按合作方拆库绕开组合风险。

## 2. 威胁模型与安全定义

把 query 表示为按声明类别排列的 0/1 行向量 `a`，公开它就向公共知识增加等式
`a·x = value`。

**安全定义（仅限精确有理线性推断）**：在所有历史已公开行与本批选中行张成的
**有理行空间**中，任何 protected 类别 `c` 的单位向量 `e_c` 都不得出现。等价地：
对每个受保护 `c`，`rank(H ∪ S ∪ {e_c}) > rank(H ∪ S)`，即公开等式组不能把
`x_c` 唯一确定下来。

明确排除在外、本题不分析的内容：

* **没有默认公开的总数或其他先验等式**：历史从空开始，只有实际公开过的等式
  参与张成；
* 不分析整数性、非负约束（攻击者只用 Q 上线性组合，不用"计数必须是非负整数"
  这类额外约束收紧推断）；
* 不分析外部知识、不分析选择结果本身的侧信道（"哪个子集被选中"泄露的信息）；
* **不声称差分隐私**：发布值是精确和，不加噪、不平滑。

历史中**实际公开过的等式永久参与**安全判断：旧请求不再被查询也不会被遗忘，
公开知识只增不减。

## 3. 知识表示：有理行空间的 RREF 基 + 受保护剩余

账本把每条已公开等式（成员集合与公开值）永久存入 `equation` 表。安全判定只依赖
这些行的**行空间**，与公开值无关。计算时（不落库）：

1. 对全部历史行在 Q 上构造**行最简形（RREF）基** `B`（`fractions.Fraction`
   精确运算，主元列两两已消元）；
2. 每个受保护单位向量 `e_c` 对 `B` 取剩余 `g_c = reduce(e_c, B)`。历史本身必然
   安全（归纳不变式），故 `g_c ≠ 0`；若为零说明账本不变式被破坏，直接报错；
3. 候选行 `v` 对 `B` 的剩余为零 ⇔ 它已在历史空间内 ⇔ 公开它不增加知识
   （仍可计效用）；否则把剩余作为新主元行扩基，并同步更新所有 `g_c`。
   扩基后某 `g_c` 变为零 ⇔ `e_c` 进入扩张后的空间 ⇔ 该集合不安全。

安全集族是**向下封闭**的（子集张成更小的空间），不安全集族向上封闭——这是
分支限界剪枝正确性的来源。所有判定都是精确有理运算；浮点秩、只查单条 query、
只查本批、只查两两差分都会漏判三条以上的组合泄露，均不合规、不予采用。

## 4. 精确优化：分支限界 + 字典序并列规则

目标：在当前完整历史下，于所有安全子集中**最大化 utility 之和**；并列时把各
选中 id 按 Unicode 排序，取 id 元组**字典序最小**者；允许空集。不得用贪心或
保守全部抑制冒充最优解（单保护类时安全集恰是拟阵独立集、贪心可行，但多保护类
是拟阵交、贪心一般不正确；本实现一律精确求解）。该选择问题一般为 NP-hard
（≥2 个保护类即等价于拟阵交），实现为按 id 升序的单次分支限界 DFS，最坏
指数级，由 22 条 query 的契约上限界；两条剪枝规则：

* **安全剪枝**：沿 DFS 维护当前集合的 RREF 基与各 `g_c`；加入候选即扩基，
  任一 `g_c` 归零则整枝剪掉（不安全集向上封闭）。已在历史空间内的候选行
  不改变基，直接计入效用。
* **效用剪枝**：`当前效用 + 剩余后缀效用和 < 已知最优` 时整枝剪掉。
* **元组剪枝**：`当前效用 + 剩余后缀效用和 == 已知最优` 且当前决策前缀已
  确定产生更差元组时整枝剪掉。依据：对两个集合 `S,T`，其排序 id 元组的大小
  由 `min(S △ T)` 属于谁决定；未决 id 全部大于已决 id，故若已决前缀与现任
  最优元组的第一个差异元素属于现任最优，则该子树所有完备化的元组都更差。

正确性义务：安全判定必须精确（Q 上 RREF，不用浮点）；最优性必须全局（不用
贪心/保守抑制替代）；并列规则必须确定（与输入数组顺序无关）。测试用独立小
规模穷举 oracle（另一套 Fraction 高斯秩实现 + 全子集枚举）随机核对最大效用
与选中集合（含并列密集的冲突对场景），并含精确线性依赖
（`{a,b}+{a,c}-{b,c}=2e_a`）、三条以上组合才泄露、重复 members、已知行重复
发布、效用贪心反例与两组并列用例。

## 5. 账本与事务边界

SQLite 表（均 `WITHOUT ROWID`）：

| 表 | 作用 |
|---|---|
| `meta(key,value)` | 固定规范私有向量（`config`）与单调历史代次（`generation`） |
| `equation(request_id, query_id, members, value)` | **永久**保留的已公开等式（行与公开值） |
| `request(request_id, request_sha256, canonical, generation, receipt)` | 规范请求身份与确定的公开回执字节 |

一次 release 的提交在**同一个短 `BEGIN IMMEDIATE` 事务**内完成：重放重查、
代次校验、写入新公开等式、推进代次（非空选中才推进）、写入规范请求身份与
回执。任何非法请求或失败求解都在打开写事务之前/之外结束，公开知识与已有
回执绝不半写。

* **代次语义**：`generation` 从 0 开始，每次**非空**选中提交后 +1（空集发布
  不改变公开知识，不推进代次，但仍记录请求与回执）。回执与 preview 中的
  "代次"均指**该选择所依据的历史代次**。
* **回执内容**：只含 `request_id`、代次、总效用和按 id 排序的选中
  `{id,members,value}`；不含被抑制 query 的值、原始私有向量或规划内部证书。
  空集成功也记录请求及代次。回执在提交时一次性序列化存库，之后永远按存储
  字节发布。
* **重放**：相同 `request_id` 且规范请求相同 → 返回原回执**字节**，即使后来
  知识已变化也不重新规划；同 ID 异请求整体拒绝（`ConflictError`，账本不变）。
  重放判定在提交事务内复查，两个进程并发提交同一 `request_id` 时后者按重放
  处理，恰好登记一次。
* **崩溃恢复**：提交与输出之间进程退出时，重启以相同请求重放即取得原回执，
  不会再次登记（等式与回执同事务原子落库）。只承诺进程崩溃恢复（SQLite
  回滚日志保证单事务原子性），不承诺断电保证。

## 6. 无长写事务的并发协调

**精确组合求解期间不得保持 SQLite 写事务**（既有 snapshot 的整段
`BEGIN IMMEDIATE` 封存方式不能直接包住求解器）。本方案采用乐观并发：

1. 在**短读事务**内一致地读出 `(代次, 全部已公开行)` 快照；
2. 在**任何事务之外**做精确求解（此时不持有任何写锁：验收测试在求解暂停点
   用第二连接成功 `BEGIN IMMEDIATE` 并回滚来验证此边界）；
3. 在短 `BEGIN IMMEDIATE` 事务内复查：`request_id` 是否已被登记（重放/冲突）、
   当前代次是否仍等于快照代次。**代次已变 ⇒ 旧计划失效，回滚并用新历史
   重新求解重试**；只有相对于实际提交前历史仍然安全且全局最优的集合才会
   成为公开事实。

正确性义务与代价：

* **不会漏判组合泄露**：提交代次校验在写锁保护下进行，"校验+写入"与任何
  其他写者串行化；两个进程从同一空历史分别求出"`{a,b}` 安全"、"`{b}` 安全"
  时，先到者提交，后到者必然观察到代次变化、针对新历史重算（`{b}` 被抑制），
  最终不会都公开。不能把"在旧快照上分别安全"的结果拼接提交。
* **求解进程被终止后不阻塞后续发布**：求解期间不持有任何锁，写事务只覆盖
  微秒级的校验与落库；进程在求解中被杀没有任何状态需要清理，在写事务中
  被杀由 SQLite 回滚日志自动回滚。
* **恢复前的旧执行者不能覆盖恢复后的决定**：旧执行者恢复后继续提交时，
  代次校验失败 ⇒ 回滚重算，只有针对新历史仍安全且最优的集合才落库。
* **重试代价**：每次重试都意味着另一次非空发布已提交；N 个并发请求最多
  引起 N(N-1) 次重算即收敛。重试上限（1000 次）仅防御病态活锁。
* **preview 不授予发布资格**：preview 只返回最优选中 id、总效用与所依据的
  历史代次（不含任何计数），不登记公开事实；release 永远按自己成功提交时
  的完整历史重新满足同一安全与最优规则，不信任先前 preview。

## 7. 可运行示例

```sh
python -m distribution_drift.disclosure_cli init    --db run/wb.db --spec fixtures/disclosure/spec.json
python -m distribution_drift.disclosure_cli preview --db run/wb.db --request fixtures/disclosure/request-ab.json
# {"generation": 0, "request_id": "partner-batch-1", "selected_ids": ["q-ab"], "total_utility": 5}
python -m distribution_drift.disclosure_cli release --db run/wb.db --request fixtures/disclosure/request-ab.json
# 提交回执：generation 0，选中 q-ab，value 120（=100+20），total_utility 5
python -m distribution_drift.disclosure_cli release --db run/wb.db --request fixtures/disclosure/request-b.json
# e_a = {a,b} - {b} 已进入公开行空间 ⇒ 整体抑制：selected []，total_utility 0，代次 1
python -m distribution_drift.disclosure_cli receipt --db run/wb.db --request-id partner-batch-1
# 原回执字节
```

`fixtures/disclosure/expected/` 保存两份确定回执用于逐字节比对。

## 8. 限额汇总

| 对象 | 上限 |
|---|---|
| 声明类别 | 2..32，唯一非空 ident |
| 每类私有计数 | 0..10⁹ 严格整数，每类恰好一次 |
| protected | 非空唯一声明子集 |
| 每请求 query 数 | 1..22，id 唯一 |
| utility | 1..10⁶ 严格整数 |
| 公开值 | 原始计数精确和，可超 10⁹ |
| 输入 JSON | ≤8 MB，严格（重复键/NaN/Infinity 拒绝） |
| release 重试 | 1000 次（每次对应一次他方非空提交） |

## 9. 测试

`tests/test_disclosure.py` 覆盖：规范与请求的严格契约（重复键、布尔、越界、
越域、顺序无关规范化）；规划器的精确线性依赖、三条以上组合才泄露、重复
members、已知行重复发布、效用贪心反例、并列规则与空集；独立穷举 oracle
随机核对；账本的规范顺序幂等、同 ID 冲突、永久历史、空集回执、重启恢复、
回执无私有字段；a/b/c、protected=[a] 联动（先 `{a,b}` 后 `{b}` 必抑制、
单独均安全、三批组合泄露）；求解暂停点第二连接写事务、陈旧执行者重算、
同请求并发恰好登记一次、两线程/两进程竞争不双公开；真实子进程求解中退出
与提交后输出前退出的恢复；CLI 全链路与失败保留；夹具逐字节比对。
